## Repository Overview

TerraTitan is an LLM-powered workflow that converts AWS CDK constructs to Terraform CDK (CDKTF). The project uses Mastra.ai as its workflow orchestration framework and is structured as a monorepo with pnpm workspaces and Turborepo.

## Definition of Concepts (L1 Constructs vs L2 Constructs)

AWSCDK and CDKTF share utilities and logics around building a Tree of Constructs which each know how to "synthesize" to a target configuration language. For AWSCDK the target configuration language is CloudFormation (JSON) and for CDKTF it is Terraform (JSON).
At the lowest level of Constructs (referred to as "L1 Constructs") these are one to one to the core configuration resources (autogenerated). For example:
- AWSCDK "L1 Constructs" are autogenerated from the CloudFormation API, creating "CfnXxx" L1 Resources
- CDKTF "L1 Constructs" are autogenerated from each Terraform Provider JSON Schema, pre-built and distributed as the "@cdktf/provider-aws" package of Terraform AWS L1 Resources

Additionally: the aws-cdk-lib package defines higher level constructs (referred to as "L2 Constructs") over the autogenerated "L1 Constructs". These higher level constructs provide strongly typed interface for string typed constructor attributes as well as an advanced "intent" focused API. Allowing a developer friendly experience defining IaC.

The purpose of the TerraTitan Conversion workflow is to "port" these L2 Constructs over to CDKTF (replacing the "CfnXxx" L1 Resources with @cdktf/provider-aws resources and potentially other terraform utility providers - for example cloudinit, tls, ...).

## Architecture Overview

### Core Structure
- **apps/core**: Main TerraTitan application built with Mastra framework
- **data/reference/**: Reference data for LLM prompting including TypeScript declarations, Terraform docs, and sample conversions
- **data/scripts/**: PoC scripts, including golang cli used by main workflow (data/scripts/tfdocs2json) required to `go install` on changes
- **packages/**: Shared configuration packages (eslint, typescript, vitest configs)

### Mastra Framework Integration
The application is built around Mastra's workflow orchestration system:

- **Workflows**: Located in `apps/core/src/mastra/workflows/` - handle complex multi-step conversion processes
- **Agents**: Located in `apps/core/src/mastra/agents/` - specialized AI agents for specific tasks like document merging
- **Storage**: Temp local storage uses LibSQL for workflow state persistence
- **Telemetry**: Configured with OpenTelemetry for observability

### Key Workflows
- `conversionWorkflow`: deprecated legacy AWS CDK to CDKTF conversion process
- `vNextConversionWorkflow`: Main AWS CDK to CDKTF conversion process
- Various PoC workflows for testing specific conversion scenarios

The current stages of the vNextConversionWorkflow are:

1. Prompt user for Conversion input:
  - Upstream Module: The AWS CDK lib module to convert based on git repo, tag, moduleName (i.e. aws-autoscaling, aws-rds, ...)
  - Workspace Name: The local directory to write converted source and unit test files to. This directory is created and the TerraConstructs/base git repository is cloned into it (if it didn't exist already)
  - Output Module: The name of the aggregate module to write converted files into. For example aws-ec2, aws-lambda, aws-ecs, ... are all aggregated under `TerraConstructs/base/src/aws/compute` - `compute` being the "output Module" for the workflow
2. Read every Upstream Module Source File and Unit Test File
3. For every Source File, identify the underpinning "L1 Construct" (if any) and find "similar" / "equivalent" terraform-provider-aws "L1 Construct" (could me multiple due to the nested nature of CFN resources compared to Terraform)
4. Keep Human In The Loop by prompting for a review of identified CDKTF References in step 3.
5. For ever Source File and every Unit Test file, generate LLM Instructions to do a first draft conversion using all the collected information for the context and few shot prompting.
6. Handle rate limits and LLM API to collect generated conversions and write them to the Workspace under the specified "Output Module"


### Data Pipeline
1. **Reference Data** (`data/reference/`):
   - `declarations/`: TypeScript declaration files for AWS CDK, Terraform providers, and TerraConstructs
   - `docs/`: Terraform provider documentation in markdown format
   - `merged/`: Combined TypeScript declarations with provider documentation stored for re-use (autogenerated by workflow if missing)

2. **Samples** (`data/samples/`): AWS CDK to CDKTF conversion examples used for few-shot prompting and validation

### Utilities and Helpers
- **RAG System** (`apps/core/src/mastra/rag/`): Retrieval-augmented generation for enhanced LLM context
- **Merge Documentation** (`apps/core/src/mastra/util/merge-docs.ts`): Combines TypeScript declarations with markdown documentation
- **Source Conversion Agents** (`apps/core/src/mastra/agents/source-converter/`): Specialized conversion logic

### Guides

- Follow `guides/provider-aws-update.md` to update the terraform provider aws version and the VectorDB embeddings for the TerraTitan workflows.
